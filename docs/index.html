Overview

simple_widgets is the missing middle layer of the Simple Eiffel GUI story. The classic chain was WEL (raw Win32) → Vision2 (portable widgets) → your application. The simple chain is simple_cairo (the substrate) → simple_widgets (the vocabulary) → your application (the intent). Before this library existed, a production face meant two thousand lines of boilerplate above the canvas; that boilerplate is now a toolkit.

Every pixel is drawn by the toolkit itself onto one cairo surface in one plain Win32 window: buttons, text boxes with spell-checking, menus, dialogs, toasts, tabs, virtualized lists, splitters, a complete file dialog. There are no child HWNDs, no common controls, no native anything - which is why every control looks identical, themes swap live, and the whole face is testable headless.

58 pages cover every class shipped across Waves 1-2, Wave 3's first batch, and one planned control kept visible on purpose; the catalog (specs/S02) plans coverage of the full desktop-and-web widget union across six waves. Part of the Simple Eiffel ecosystem.

Architecture: five layers (spec S01)

LayerWho lives thereCharacter
COMPOSITIONYour application Pure intent - what exists and what happens
COMPONENTSW_FILE_DIALOG, cards, groups Widgets assembled into meaningful units
WIDGETSW_BUTTON … SW_LIST Controls: state, contracts, input handlers
PAINTERSW_PAINTER, SW_THEME The drawing vocabulary and the visual truth
SURFACESW_WINDOW over simple_shell Deferred SHELL_WINDOW effected: native window, event pump, cairo surface - simple_widgets itself is pure Eiffel, zero C

Higher layers are simpler and faster to use; lower layers are more expressive and more verbose. Applications normally live at the top two; the escape hatches down are deliberate and rarely needed.

The rules the toolkit lives by

#Rule
R1One language: Eiffel over inline C externals; no separate C toolchain steps.
R2Painter monopoly: only SW_PAINTER touches CAIRO_CONTEXT.
R3Contracts everywhere: state machines carry invariants; protocols carry pre/postconditions.
R4Theme is truth: no literal colours or sizes in widgets - tokens only.
R5Agents wire behaviour: on_change/on_select/actions, never inheritance-to-configure.
R6Immediate feedback: every interaction shows its effect now (toast, status, preview).
R7Nothing native: menus, dialogs, toasts, file dialogs - all drawn. OS services without pixels (clipboard, keys, spelling) are welcome.
R8Unicode first: STRING_32 through every API; surrogate pairs handled at the borders.

Quick Start

Installation

  1. Add to your ECF: 
    <library name="simple_widgets" location="$SIMPLE_EIFFEL/simple_widgets/simple_widgets.ecf"/>
  2. Ship cairo.dll beside your executable (every finalize wipes F_code - copy it back).
  3. For shaped text (bidi, script fallback, colour emoji) also stage LICENSE-ASSETS.md and assets/noto-emoji/png/128/ beside the exe - tools/stage_runnable.sh <folder> does all three - and call window.enable_shaped_text. See SW_PAINTER.

A whole application

local
    window: SW_WINDOW
    theme: SW_THEME
    root: SW_COLUMN
do
    create theme.make_dark
    create window.make ("hello", 100, 100, 900, 700, theme)
    create root.make
    root := root.with_padding (16.0).with_gap (12.0)
    root.put (create {SW_LABEL}.make_body ("Every pixel here is the toolkit's own."))
    root.put (create {SW_BUTTON}.make_primary ("Go", agent on_go))
    window.set_root (root)
    window.run
end

The living cookbook is demo/sw_demo.e - the showroom exercising every control; build it with the commands under Testing.

Margins and padding

Controls do not sit on the window edge. The toolkit carries Vision2's spacing model as three theme tokens, and every one of them scales with the text - an application drawing at 2x (theme.set_text_scale (2.0)) gets 2x margins without touching a layout.

Vision2 (EV_BOX, ISE 25.02)simple_widgets1xMeaning
EV_BOX.border_widthSW_THEME.border_width12 pxspace between a container's edge and its content
EV_BOX.padding / padding_widthSW_THEME.padding8 pxspace between siblings
no Vision2 name - a native control owns its own marginsSW_THEME.control_inset11 pxspace between a control's edge and its label
EV_LAYOUT_CONSTANTS.default_button_heightSW_PAINTER.min_control_heightmeasuredascent + descent + 2 × control_inset
EV_LAYOUT_CONSTANTS.dialog_unit_to_pixelsSW_THEME.text_scale×1.0the one knob every token is multiplied by
no Vision2 nameSW_THEME.scrollbar_width12 pxthe column a vertical scrollbar takes (0.20.0)
no Vision2 nameSW_THEME.min_thumb24 pxthe shortest a scrollbar thumb draws, so it stays grabbable (0.20.0)

The border is applied once. SW_WINDOW insets its root by theme.border_width on all four sides (SW_WINDOW.content_border), and SW_DIALOG does the same inside its card. Plain boxes keep a 0 border of their own - exactly as Vision2 defaults EV_BOX.border_width to 0 (EV_BOX_I.Default_border_width) and lets the dialog set it (EV_MESSAGE_DIALOG does vb.set_border_width (10)) - so nesting cannot double it. SW_CARD, SW_GROUP and SW_FILE_DIALOG are surfaces in their own right and keep one.

An explicit value always wins. with_padding / set_padding and with_gap / set_gap mark the box explicit, and an explicit value - including 0.0 - is never overwritten by the theme at any scale.

Controls are never smaller than their font. SW_PAINTER.text_extent is cairo's own font ascent + descent for the selected font, so it already carries the scale; min_control_height adds the inside inset above and below. Measured 1x → 2x: button 38 → 75, text box 42 → 80, check box 38 → 75, number box 38 → 75, label 24 → 47 px.

The document view and the shared building blocks

SW_DOCUMENT_VIEW (0.22.0) reads and edits a rich document: a commentary, a lexicon entry, a dictionary article or a library document. The model lives in simple_document: SIMPLE_DOCUMENT, an ordered list of DOC_BLOCKs (paragraphs, headings of three levels, bulleted and numbered items, block quotes, code blocks, rules and tables). Every text is a DOC_TEXT with inline bold, italic, small capitals, superscript, inline code, strikethrough and links that carry a target. SW_DOCUMENT, SW_DOC_BLOCK and SW_RICH_TEXT no longer exist. SW_DOC_STYLES flattens a DOC_TEXT for the shaper. The model knows no markup; a codec turns it into source and back.

The view draws links in the theme's ink_accent, calls on_link_click (target) when one is followed, reports on_link_hover, selects across blocks and table cells, and copies with Ctrl+C. Hover cards come from set_hover_card_builder, as in the paragraph list. A Hebrew paragraph sits flush right.

Live-preview editing (0.22.0)

Give the view a codec with set_codec (usually SW_MARKDOWN_CODEC, built on simple_markdown) and it edits. Click a block and a box opens over it holding the block's Markdown. Every other block stays formatted. Click elsewhere to keep the edit. Escape drops it. Ctrl+Enter keeps it and opens a new paragraph. Ctrl+click follows a link. The document changes only when an edit is kept. SW_DOCUMENT_CODEC is the deferred class a host can effect for another markup.

Two small changes came with it. SW_KEYS.simulate fixes the modifier state for tests, so a key held on the real keyboard cannot turn a test's click into a Ctrl+click. SW_SPELLER no longer marks Hebrew or Greek words.

Dependencies: besides simple_shell and simple_cairo, the view needs simple_document and simple_markdown.

Parallel text (0.24.0)

SW_PARALLEL_TEXT shows versions side by side, verse by verse. Rows are canonical verses and columns are versions (up to six, each with a weight, a text scale and an alignment). Each cell is a DOC_TEXT, wrapped and shaped in its own direction, so a Hebrew column sits flush right. A row is as tall as its tallest cell. There is one scroll, and the column titles stay put while the rows scroll. A note row ("LXX 9 = MT 9-10") spans every column in muted text. Each cell has its own marks, painted through a legend ("agrees with LXX"). cell_at and on_cell_click answer which cell the pointer is on, and scroll_to_row brings a verse into view. Selecting copies a row's cells separated by tabs and the rows one per line. Spacing comes from the theme tokens.

Interlinear (0.25.0)

SW_INTERLINEAR shows a text as stacked word cells: the surface word, transliteration (italic), pronunciation, gloss, lemma, Strong's number and morphology in English. Cells flow and wrap, right to left for Hebrew and left to right for Greek. set_line_visible hides any line except the surface word. A click, Left and Right (in reading order), Home and End select a word (on_token_select); token_at names the word under a point; Ctrl+C copies a word's lines; a rest on a word opens the card that set_hover_card_builder builds. It inherits SW_DOC_UNITS alone.

Grouped bars and the chart chassis (0.26.0, 0.27.0)

SW_BAR_CHART.set_series names the series and add_group (label, values) adds a category with one value for each series. A group's bars stand side by side, a legend names the series, series_at says which bar is under a point, and set_emphasized_series draws the other series in the theme's pale ink. SW_CHART.draw_chip is the one hover chip for every chart and stays inside the frame. The chassis draws the legend from legend_names and ends it in "+n" when the names do not fit. series_color gives eight distinct colors before it cycles.

Query builder (0.27.0)

SW_QUERY_BUILDER builds a clause tree. The deferred SW_QUERY_NODE has three heirs: SW_QUERY_GROUP (children joined ALL or ANY, nested to any depth), SW_QUERY_CONDITION (field, operator, value) and SW_QUERY_PROXIMITY (two words within n words of each other, NEAR/n or BEFORE/n). Any node can be negated. The engine reads root; expression is the question as a reader reads it; query_text is an SQL-shaped rendering for display only, never executed. set_field_choices gives a field a picker of codes and set_field_suggester makes a field a lemma whose picker follows the typing. on_change hears every edit, including a proximity's distance (0.28.1). The first builder's flat calls still work on the root group.

One hundred thousand rows (0.28.0)

SW_DATA_GRID draws only the rows in view; GW-29 measured it with 100,000 rows of shaped Hebrew and Greek cells. The cost was in simple_shaping's cache contracts (fixed in simple_shaping 0.6.1). SW_SHAPING.layout_styled now keeps two generations of 1,024 layouts, so a string drawn again is one hash lookup; the font setters clear it, and forget_layouts covers changes made on facade directly. SW_GRID_COLUMN.sort_key gives each row's key once per sort. Measured in the lean build (the shipping configuration): wheel frame 1.5 milliseconds median, page jump 5.1 milliseconds, sort 175 milliseconds, against a 16.7 millisecond frame. With every contract on (0.28.2): wheel frame 14.8 milliseconds, page jump 42.6 milliseconds; the lean build is 1.5 and 5.1. The GW-29 test times only the measured step inside simple_testing's without_contracts, with contracts switched off for that step: wheel frame 3.7 milliseconds, page jump 13.6 milliseconds, and it asserts the 60 Hz budget in every build. The grid's merge runs over SPECIAL arrays, and 100,000 rows sort in about 190 milliseconds. SW_DATA_GRID.add_row (0.28.2) places one row by binary search, add_rows adds many with one rebuild, and SW_GRID_COLUMN.alignment (set_alignment, aligned) sets a column's alignment; the default, Align_start, puts a Hebrew line flush right.

Shared building blocks (0.25.0)

  • SW_TEXT_POINTING, SW_VSCROLLING, SW_TEXT_SELECTION, SW_IN_PLACE_EDITING, SW_STACKED_ITEMS and SW_DOC_UNITS are deferred ancestors. A widget inherits them side by side (Eiffel multiple inheritance), because none of them redefines another's SW_WIDGET features. Two composed bases do the joining once, so each widget names one parent: SW_STACKED_POINTING joins pointing, scrolling and the stack, and SW_DOC_UNITS (the units of stacked texts and cells, lifted from the document view) inherits it together with SW_TEXT_SELECTION. SW_PARALLEL_TEXT's inherit clause is a single parent. SW_MARK_HOST is a mixin with no parent at all (legend and mark painter), shared by the text box, the paragraph list and the parallel text. SW_DOCUMENT_VIEW and SW_PARAGRAPH_LIST stand on these too, as do SW_PARALLEL_TEXT and SW_INTERLINEAR. SW_DOC_UNITS also owns its heirs' input and layout bookkeeping, and SW_STACKED_ITEMS.pinned_height keeps a band that does not scroll out of the content.
  • SW_VSCROLLBAR is the one vertical scrollbar. Lists, paragraph lists, scroll areas, chat threads, trees and data grids all use it. Its drag keeps the grab point and ends on release.
  • SW_BLOCK_STACK stacks items of different heights and finds the item under a point by binary search.
  • SW_WORD_BOUNDARY is the one definition of what a word is.
  • The theme tokens scrollbar_width (12 px at 1x) and min_thumb (24 px at 1x) size the scrollbar and scale with the text.

Testing: the contract assault

The library ships a test target that drives the model layer headless - including drawing, via a painter over an offscreen cairo surface - with every assertion live (F_code with contracts kept). 444 tests at 0.28.2 (75 across ten assault sets at first); the suite caught three real defects on its first day (a truncation alias in list row math, a clipboard race against history managers, and an ECF namespace clash). 

# build the demo showroom
/d/prod/ec.sh test -config simple_widgets.ecf -target sw_demo

# build and run the contract assault
/d/prod/ec.sh test -config simple_widgets.ecf -target simple_widgets_tests
cp $SIMPLE_EIFFEL/simple_cairo/cairo.dll EIFGENs/simple_widgets_tests/F_code/
./EIFGENs/simple_widgets_tests/F_code/simple_widgets.exe

Platform notes

  • Windows only today: the SURFACE layer is Win32; spelling is ISpellChecker (Windows 8+). Everything above the surface is portable by design.
  • Per-monitor DPI aware; all coordinates are physical pixels.
  • Dark and light palettes ship; dark is the house default.
