Description

Word-wrapped bubbles by role, wheel scrolling, and the stickiness law every chat client honours: the thread follows its tail until the reader scrolls back up, and appends stop yanking. append_to_last grows the last bubble in place - the streaming substrate. Model and streaming assaulted headless.

Source: src/sw_chat_thread.e · since Wave 6 (2026-08-22). Live in the showroom: demo/sw_demo.e.

A conversation

create th.make
th.add_message (th.Role_mine, class="string">"hello")
th.add_message (th.Role_theirs, class="string">"")
th.append_to_last (class="string">"wor")
th.append_to_last (class="string">"ld")

Shaped bubbles (simple_shaping)

Give the window a shaping kit and this widget uses it without another line of application code:

window.enable_shaped_text

Bubbles are then laid out by SIMPLE_SHAPING.layout: Hebrew reads right-to-left inside a left-to-right pane, Greek keeps its accents, and an emoji is the same shipped Noto picture on every member's screen. Bubble height comes from layout.total_height - never a line count times a constant - and the greedy word wrap is skipped entirely.

  • shaped_layouts - one SHAPED_LAYOUT per PARAGRAPH, in messages order, once a shaped frame has been drawn. Empty on the toy path and before the first frame. A message with no line breaks is one paragraph, so single-paragraph traffic is still one layout per message.
  • layout_spans - one entry per message OF THE LAST LAID-OUT FRAME: that message's paragraph layouts are shaped_layouts [base .. base + span - 1]. Between two frames it lags, because only SW_SHAPING.layout_for can make a layout and only at a width the widget learns from the painter inside draw. The invariant asks laid_out_revision = revision before demanding one span per message; in 0.6.0 it demanded it unconditionally, and add_message after a first shaped frame broke it (0.6.1).
  • laid_out_width, laid_out_size - the bubble inner width (pixels) and type size the current layouts were built for.
  • revision / laid_out_revision - the content clock. They differ exactly when the layouts are stale.

R10, re-layout at resize END. A width change waits for SW_PAINTER.is_resize_storm to clear, so dragging the frame costs zero shaping calls. A content change never waits: a message that arrives mid-drag still appears.

Nothing in the public model changes on either path - add_message, append_to_last, stickiness, content_h and handle_wheel behave exactly as they always have.

Line breaks (0.6.0)

The square boxes. Until 0.6.0 neither path had heard of a newline. The toy wrap split on the SPACE CHARACTER ALONE, so an LF was another character inside a "word" and cairo drew it as .notdef - the box. The shaped path failed more quietly: simple_shaping counts LF among the characters a line MAY break at, so the text wrapped near the break but the LF itself was still shaped and still painted.

A message is now cut into PARAGRAPHS before either path lays anything out:

in the messagewhat happens
LFends the line; never drawn
CRLFONE break, not two
a lone CRends the line; never drawn
TABbecomes a space (there are no tab stops here)
two or more breaksat most ONE empty line - a bounded blank
a trailing breakdropped: no empty last line
thread.paragraphs_of (some_text)   -- the cut, public and contracted
thread.display_text (i)            -- message i as the bubble SHOWS it

Wrapping applies WITHIN a paragraph and a bubble's height is its real line count. wrapped is public now and honours breaks.

Selecting and copying (0.6.0)

A bubble is selectable text, not a picture of text. Press and drag to select; double-click takes the word; Escape clears; Ctrl+C - or the right-click menu (Copy, Select Message, Select None) - copies through SW_CLIPBOARD, the same door SW_TEXT_BOX uses.

thread.has_selection      -- is there a range?
thread.selected_text      -- exactly what copy_selection hands the clipboard
thread.select_message (2) -- the whole of bubble 2
thread.clear_selection

Granularity is per CHARACTER on the toy path and per GLYPH CLUSTER on the shaped path, walked over GLYPH_RUN's own cluster_map and x_positions - SHAPED_LINE reserves character_index_at_x for a future simple_shaping cycle and does not implement it. In a right-to-left run the boundary at a cluster's LEFT edge is the caret AFTER that character.

Selection lives inside ONE bubble. A drag that wanders out runs to the anchor bubble's own ends and stops. A thread is a list of utterances by different speakers; a range spanning three of them has no honest text to hand the clipboard. Cross-bubble selection is not supported and is not planned.

A press inside a bubble is CONSUMED now (the pane needs the pointer capture to receive the drag) and cursor_kind is the I-beam. A press on bare pane clears the selection and still bubbles up, as before.

The per-message menu (0.7.0)

A bubble used to be write-once: add_message put one on the thread and append_to_last grew it while a stream ran, and after that nothing could change it. A chat server does not work that way - it folds edit, delete and reaction events over the message they name, and a reply is a message carrying a parent's id. There is now a door for each.

thread.set_message (2, {SW_CHAT_THREAD}.Role_keep, "the corrected text")
thread.mark_edited (2)                       -- a small muted "edited" marker
thread.tombstone (3)                         -- a placeholder, never a gap
thread.set_reactions (4, row)                -- emoji + tally chips, mine outlined
thread.set_reply_quote (5, "Ada", "the parent message")

thread.is_edited (2)        thread.is_tombstone (3)
thread.reactions_of (4)     thread.has_reply_quote (5)
thread.reply_quote (5)      thread.quote_line (5)     thread.drawn_quote (5)
thread.bubble_height (4)    -- what the last frame measured it at

thread.message_at (px, py)  -- which bubble, 0 for none
thread.reaction_at (px, py) -- [message, emoji], or [0, ""] off every chip

Role_keep is not a role: it is what an edit passes when the words change and the speaker does not, which is what a server's edit event actually carries.

Every one of these is a CONTENT CHANGE, and that is the whole safety story. A content change has meant "bump revision" since 0.5.0, so laid_out_revision lags, spans_match_when_current goes quiet for exactly one frame, and refresh_layouts rebuilds and records - the same door add_message has gone through since 0.6.1. None of them re-shapes: a span indexes layouts only SW_SHAPING.layout_for can make, at a width and a pixel size the widget does not learn until draw.

A delete is a tombstone, never a gap. The bubble keeps its place at reduced height, muted, reading message deleted - the ORDER of a thread is part of its record, and a vanished bubble silently rewrites who answered whom. The text is really destroyed (emptied, not hidden), so no selection can reach it and copy_selection has nothing to take. Every decoration goes with it, and the tombstone is terminal: the other four commands require a live message.

Four bands, all measured. Reply quote (one line, elided at the inner width), text, "edited" marker, reaction row (wraps rather than run off the bubble's edge). Each changes the bubble's height, therefore content_h, therefore the thumb - and stickiness survives all of it the way add_message preserves it. The quote and each chip's emoji go through the shaping kit when there is one and fall back to cairo's toy metrics when there is not. The decoration layouts are kept OUT of shaped_layouts: it is tiled exactly by layout_spans.

Known limits

  • Plain text bubbles - links, code spans and images await the rich-text substrate.
  • Selection is within ONE bubble. Cross-bubble selection is deliberately not supported.
  • A tombstone is terminal: set_message, mark_edited, set_reactions and set_reply_quote all require a live message, so a deleted bubble cannot be edited back into speech.
  • The "edited" marker and the tombstone placeholder are drawn on the TOY path in both modes - they are fixed ASCII, and mixing a shaped layout into a two-word marker buys nothing. The quote and the reaction pictures ARE shaped when a kit is there.
  • A reaction chip is emoji + tally. There is no hover card naming who reacted: the widget is never told, and the server has already deduped per person.
  • A run of blank lines collapses to one empty line, and a trailing blank line is dropped. Deliberate: a bubble must not be inflatable by padding.
  • Shaped bubbles are left-aligned inside the bubble whatever the paragraph direction; an RTL paragraph is not yet right-aligned to the bubble's inner edge.
  • The shaping kit needs its runnable folder: cairo.dll, LICENSE-ASSETS.md and assets/noto-emoji/png/128/ beside the executable. Use tools/stage_runnable.sh. Missing artwork degrades to a note and a box, never a crash.

Bugs & gotchas

  • Bubble heights are measured during draw; content_h is 0 before the first frame - scroll math self-corrects at that frame.
  • Hit-testing answers from the geometry the LAST draw recorded. Before the first frame, and for a message added since it, a press finds no bubble and simply clears the selection.

Extension plans & possibilities

  • Timestamps; avatars via SW_AVATAR; per-range styling when the substrate lands.
  • A built-in context menu for the mutation gestures. It is deliberately the host's for now: only the host knows which of reply/react/edit/delete this reader is allowed on this message, and a menu that offers Delete on somebody else's words is worse than no menu.
